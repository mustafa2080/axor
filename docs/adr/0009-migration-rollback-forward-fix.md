# ADR-0009: استراتيجية الـ rollback للـ migrations (forward-fix فقط)

- **الحالة:** منفّذ (2026-10-27) — بند «استراتيجية الـ rollback» من المرحلة B و§13 في `TASKS.md`.
- **السياق:** Drizzle بيولّد migrations للأمام بس، ومفيش `down`. وMariaDB مبتدعمش DDL داخل transaction: لو migration فيها 3 أوامر ووقعت عند التاني، أول أمر بيفضل متطبق. فمحتاجين قاعدة واضحة لما migration تطلع غلط، وحاجة آلية تمنع الأخطاء الشائعة قبل ما توصل للـ CI.

## القرار

1. **للأمام بس (forward-fix):** مفيش `down migrations`. لو migration اتطبقت وطلعت غلط، بنكتب migration جديدة تصلحها. ما بنرجّعش migration اتطبقت ولا بنعدّل فيها.
2. **الـ migration اللي اتعملها commit مبتتعدّلش:** كل ملف `.sql` ليه checksum (SHA-256 بعد توحيد نهايات الأسطر CRLF/LF) في `backend/src/database/migrations/checksums.json`. اختبار `migration-policy.test.ts` بيفشل لو ملف اتعدّل، أو ملف من غير checksum، أو checksum لملف اتمسح، أو الـ journal فيه فجوة أو ملف ناقص أو زيادة.
3. **بعد `pnpm db:generate` شغّل `pnpm db:lock`:** بيسجّل checksum الـ migration الجديدة بس. وبيرفض يشتغل (exit 1) لو migration مسجّلة قبل كده اتغيّرت.
4. **الأوامر المدمّرة محتاجة موافقة صريحة:** أي migration فيها `DROP` أو `TRUNCATE` أو `DELETE FROM` أو `RENAME` أو `MODIFY` أو `CHANGE` لازم تحتوي سطر `-- destructive-approved: <السبب>` بسبب مكتوب (سطر فاضي مش بيعدّي)، وإلا الاختبار بيفشل. التعليقات مش بتتحسب.
5. **Expand ثم contract:** أي تغيير يكسر النسخة القديمة من التطبيق بيتقسم على إصدارين: (أ) migration بتضيف العمود أو الجدول الجديد والكود بيشتغل بالاتنين، (ب) بعد ما كل النسخ اتحدّثت، migration تانية بتشيل القديم (وهي اللي بتحتاج `destructive-approved`).
6. **migration صغيرة، تغيير منطقي واحد:** عشان فشلها في النص (بسبب إن DDL مش transactional) يسيب حالة سهلة الفهم والإصلاح.
7. **نسخة احتياطية قبل أي migration على قاعدة فيها بيانات حقيقية:** ده الـ rollback الفعلي للبيانات. الخطوة دي جزء من runbook النشر ([`docs/runbooks/deploy.md`](../runbooks/deploy.md))، وإجراءات النسخ والاستعادة في [`backup-restore.md`](../runbooks/backup-restore.md).

## لو migration فشلت في النص

1. وقّف النشر ولا تشغّل الإصدار الجديد من التطبيق.
2. شوف الجدول `__drizzle_migrations`: الـ migration ما اتسجّلتش، لكن أول أوامرها ممكن تكون اتطبقت.
3. اكتب migration جديدة تكمل أو تصلح الحالة الجزئية (مثلاً `ADD ... ` بشرط عدم وجود العمود)، أو استرجع النسخة الاحتياطية لو الحالة مش مفهومة.
4. متعدّلش الملف الفاشل بعد ما اتعمل له commit؛ الاختبار هيرفضه.

## خارج النطاق

- **تجربة استعادة نسخة احتياطية دورية على بيئة حقيقية** (البند في §7 و§12): اتعملت تجربة واحدة محلية في 2026-10-27 (`axor_dev` ← `axor_test`، الصفوف والـ checksums متطابقة) وموثّقة في `backup-restore.md`. الباقي (staging، تشفير، نسخ خارج الجهاز، جدولة) لسه محتاج بيئة وقرار منصة.
- ربط الـ checksum بقاعدة البيانات المطبّقة (مقارنة ما اتطبق فعلياً بالملفات): Drizzle نفسه بيخزّن hash لكل migration، فمش محتاجين نكرر ده دلوقتي.

## النتائج

- أي تعديل في migration قديمة أو أمر مدمّر من غير موافقة بيتوقف في `pnpm test` وفي الـ CI قبل ما يوصل لقاعدة بيانات حقيقية (الـ pre-commit hook بيشغّل lint وtypecheck بس، مش الاختبارات).
- الـ rollback مسؤولية بشرية موثقة (forward-fix أو استعادة نسخة)، مش وهم إن في «تراجع» تلقائي.
- إضافة خطوة واحدة في كل migration جديدة: `pnpm db:lock`.
