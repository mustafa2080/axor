# Runbook: النسخ الاحتياطي والاستعادة

> **الحالة:** الأوامر اتجرّبت محلياً على MariaDB 12.3 (Windows) بتاريخ 2026-10-27. ما اتجرّبش على بيئة حقيقية، وما اتجرّبش تشفير ولا نسخ خارج الجهاز (مفيش مخزن اتحدّد). أهداف RPO/RTO تحت **مقترحة** ومحتاجة اعتماد.

## إيه اللي بيتنسخ

- **قاعدة بيانات التطبيق كلها** (12 جدول حالياً بما فيهم `__drizzle_migrations`).
- **الأسرار (`JWT_ACCESS_SECRET` وغيره) مش جزء من النسخة.** مكانها مخزن الأسرار. فقدان السر مش بيضيّع بيانات: بيبطّل الـ access tokens بس، والـ refresh tokens (محفوظة في القاعدة) بتجدّد الجلسات.
- **الكود** في Git، مش محتاج نسخ احتياطي منفصل.

## النسخة حساسة

الـ dump فيه إيميلات المستخدمين وهاشات كلمات السر (Argon2id) وهاشات الـ refresh tokens وسجل التدقيق (IP وuser agent). يعني:

- تتشفّر قبل ما تتنقل أو تتخزّن. الأداة **ينتظر قرار** (لم تُجرَّب).
- صلاحية الوصول لأقل عدد ممكن، وتتخزّن بعيد عن السيرفر نفسه.
- ماتتحطش في المستودع. `.gitignore` بيتجاهل `axor_*.sql` و`*.sql.gz` و`*.sql.enc` و`*.dump` (مش كل `*.sql`، لأن الـ migrations نفسها `.sql` ولازم تتعمل لها commit)، فسمّي النسخة بأحد الأنماط دي وخزّنها برّه المستودع.
- بيئة الاختبار مفيش فيها بيانات إنتاج من غير إخفاء (بند §12).

## أهداف RPO/RTO (مقترحة، مش معتمدة)

| الهدف | القيمة المقترحة | السبب |
|---|---|---|
| RPO | حتى 24 ساعة (نسخة يومية) | الاشتراكات والتجارب بتتغير ببطء نسبياً. التغييرات اللي بعد آخر نسخة بتضيع من القاعدة (`audit_logs` و`subscription_events` كمان بترجع لوقت النسخة)، وممكن إعادة إدخالها يدوياً من لوج الـ API |
| RTO | حتى 4 ساعات | الاستعادة نفسها دقايق لحجم البيانات الحالي، والباقي زمن التشخيص والنشر |

لما فيه دفع أو عدد عملاء كبير، RPO لازم ينزل (نسخة أكتر تكراراً أو binlog للاستعادة لنقطة زمنية). **ينتظر قرار المدير.**

## أخذ نسخة احتياطية

**اتجرّب** ✅ (2026-10-27، `axor_dev`، 46,947 بايت، أقل من ثانية):

```powershell
# كلمة السر من متغير بيئة للعملية بس، مش في سطر الأوامر
$env:MYSQL_PWD = '<من مخزن الأسرار>'
mariadb-dump -u axor_app -h 127.0.0.1 --single-transaction --routines --triggers `
  --default-character-set=utf8mb4 axor_dev --result-file=axor_YYYYMMDD_HHMM.sql
Remove-Item Env:MYSQL_PWD
```

- `--single-transaction` بياخد لقطة متسقة لجداول InnoDB من غير ما يقفل الكتابة.
- `--default-character-set=utf8mb4` مهم عشان العربي.
- على Windows مسار الأداة: `C:\Program Files\MariaDB 12.3\bin\mariadb-dump.exe` (مش في الـ PATH).
- يُفضَّل ملف خيارات (`--defaults-extra-file`) بدل المتغير؛ **ما اتجرّبش**.

## الاستعادة

**القاعدة الذهبية:** استعد في قاعدة **مؤقتة أو بديلة** الأول، وتحقق، وبعدها بدّل. ماتستعدش فوق الإنتاج مباشرة إلا لو مفيش بديل.

1. **وقّف الـ API** (أو حوّل الترافيك) عشان مفيش كتابة أثناء الاستعادة.
2. **أنشئ/فضّي القاعدة الهدف.** القاعدة لازم تكون فاضية، لأن الجداول الزيادة مش بتتمسح من الـ dump. **اتجرّب** ✅ بمسح كل جداول الهدف مع `SET FOREIGN_KEY_CHECKS=0`.
3. **استعد:**
   ```powershell
   mariadb -u axor_app -h 127.0.0.1 --default-character-set=utf8mb4 axor_restore `
     -e "source C:/path/to/axor_YYYYMMDD_HHMM.sql"
   ```
   استخدم `-e "source ..."` بدل pipe من PowerShell (`Get-Content | mariadb`)، لأن الـ pipe ممكن يبوّظ الترميز. **اتجرّب** ✅ (حوالي ثانية).
4. **تحقق** (تحت).
5. **طبّق أي migrations جديدة:** `node dist/database/migrate-cli.js` من مجلد `backend`. لو النسخة قديمة هتلحق الباقي، ولو مفيش جديد بتخرج `Migrations applied.` من غير تغيير.
6. **إجراء أمني بعد الاستعادة** (تحت)، ثم شغّل الـ API وتحقق بـ `/api/v1/health/ready`.

### التحقق من الاستعادة

لكل جدول، قارن بين الأصل والمستعاد: `SELECT COUNT(*)` و`CHECKSUM TABLE`. **اتجرّب** ✅. لو مفيش وصول للأصل (كارثة)، اكتفِ بعدد الصفوف المتوقع من آخر نسخة وبتشغيل `/health/ready` ودخول بحساب فحص.

### إجراء أمني بعد استعادة نسخة قديمة

النسخة بترجّع حالة الجلسات وكلمات السر لوقت أخدها. فأي حاجة اتغيّرت بعدها بترجع **للحالة القديمة**:

- جلسات refresh اللي اتلغت بعد النسخة (خروج، أو كشف إعادة استخدام token مسروق، أو تغيير كلمة سر) **ترجع صالحة**.
- مستخدم غيّر كلمة سره بعد النسخة بيرجع لكلمة السر القديمة.
- مستخدم أو شركة اتعطّلوا بعد النسخة بيرجعوا مفعّلين.

الإجراء الأبسط والأأمن بعد أي استعادة من نسخة قديمة هو تسجيل خروج الكل:

```sql
UPDATE refresh_sessions SET revoked_at = UTC_TIMESTAMP(3) WHERE revoked_at IS NULL;
UPDATE users SET password_changed_at = UTC_TIMESTAMP(3);
```

التاني بيبطّل كل الـ access tokens الصادرة قبله (المستخدم بيسجّل دخول من جديد). **اتجرّب** ✅ على بيانات الاختبار جوه transaction وبعدها rollback: الـ SQL سليم وغيّر 5 جلسات و9 مستخدمين.

كمان راجع يدوياً (من لوج الـ API أو تقارير الدعم، لأن `audit_logs` نفسها بترجع لوقت النسخة) أي مستخدم أو شركة اتعطّلوا بعد وقت النسخة وعطّلهم تاني.

## مفتوح

- جدولة النسخ اليومية وتشفيرها ونقلها وسياسة الاحتفاظ (كام نسخة نحتفظ بيها): **ينتظر قرار المنصة**.
- استعادة لنقطة زمنية (binlog): غير مفعّلة ولم تُدرس.
- تجربة استعادة دورية على staging: مفيش staging.
- تنبيه لو النسخة الليلة فشلت: مفيش مراقبة.
