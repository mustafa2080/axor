# Runbook: الأعطال (الخدمة وقاعدة البيانات والبريد)

> **الحالة:** تشخيص وإجراءات مبنية على سلوك النظام الموجود فعلاً. مفيش مراقبة ولا تنبيهات (`infra/monitoring/` فاضي)، فالكشف عن العطل حالياً يدوي أو من شكاوى العملاء. الخطوات ما اتجرّبتش في حادث حقيقي، غير اللي معلَّم «اتجرّب».

## أول 5 دقايق (أي عطل)

1. **حدّد النطاق:** الكل واقع ولا جزء؟ الواجهة ولا الـ API؟
2. `GET /api/v1/health` ← لو مش بيرد: العملية واقعة أو الـ proxy.
3. `GET /api/v1/health/ready` ← `503` يعني الخادم شغّال لكن القاعدة مش واصلة. (**اتجرّب** ✅ حالة `ready`؛ حالة 503 متغطية باختبار.)
4. **اقرا اللوج.** كل طلب ليه `x-request-id` في الهيدر وفي اللوج، فلو عميل بلّغ بمشكلة اطلب منه الـ id. اللوج مش بيحتوي توكنات ولا كلمات سر ولا query string (متحقق منه بالاختبار).
5. **آخر نشر؟** لو العطل بدأ بعد نشر، التراجع أسرع من التشخيص ([deploy.md](./deploy.md)).

## الخدمة (الـ API) واقعة أو بتعمل 5xx

| العَرَض | السبب المحتمل | الإجراء |
|---|---|---|
| العملية مش بتشتغل وبتخرج فوراً | متغير بيئة غلط أو ناقص: الخادم بيرفض يشتغل (fail fast) | اقرا رسالة الخطأ في أول اللوج. أشهر حالة: `JWT_ACCESS_SECRET` أقل من 32 حرف أو لسه `CHANGE_ME` |
| `EADDRINUSE` | البورت مشغول | شوف مين على `API_PORT` وأوقفه |
| `/health` تمام و`/health/ready` = 503 | القاعدة واقعة أو بيانات الاتصال غلط | اتبع «قاعدة البيانات» تحت |
| 5xx في اللوج بعد نشر | كود أو migration | تراجع عن التطبيق، وراجع [deploy.md](./deploy.md) (مع انتباه لقيد الـ migration) |
| كل المستخدمين بيتعمل لهم 401 فجأة | `JWT_ACCESS_SECRET` اتغيّر أو اختلف بين نسختين | رجّع السر القديم، أو سيب المستخدمين يجدّدوا الجلسة (الـ refresh بيصلّحها من غير خروج) |
| دخول مرفوض (403) من الواجهة | `WEB_ORIGIN` مش مطابق تماماً للعنوان الفعلي | صحّح `WEB_ORIGIN` (مطابقة تامة، بالبروتوكول والبورت) |
| الـ rate limit بيحظر ناس كتير بشكل غريب | `TRUST_PROXY=false` خلف proxy فكل الطلبات جاية من IP واحد | اضبط `TRUST_PROXY=true` **بس** لو الـ proxy بتاعك |
| اشتراكات انتهت تواريخها ولسه حالتها قديمة | مهمة الانتهاء واقفة | الوصول نفسه مش بيعتمد عليها (بيقف عند تاريخ النهاية بالضبط، ADR-0007). دور على `subscription expiry pass failed` في اللوج. إعادة تشغيل الـ API بتشغّلها تاني |

**ملاحظة instance واحد:** مفيش failover. لو العملية وقعت، الخدمة واقعة لحد ما تتشغّل تاني. **ينتظر قرار المنصة** (restart policy أو supervisor).

## قاعدة البيانات

### مش واصلة (`/health/ready` = 503)

1. هل خدمة MariaDB شغّالة؟ (على Windows المحلي اسمها `MariaDB`.)
2. جرّب الاتصال بنفس بيانات `DATABASE_URL` بـ `mariadb` من نفس الجهاز.
3. بيانات الاتصال أو كلمة السر اتغيّرت؟ المستخدم متعطّل؟ الشبكة؟ الاتصالات القصوى؟
4. لما القاعدة ترجع، راجع `/health/ready`. الفحص بيتعمل في كل طلب والـ connection pool المفروض يعيد الاتصال، **لكن ده ما اتجرّبش**؛ لو فضل `503` والقاعدة شغّالة، أعد تشغيل الـ API.
5. **ماتعدّلش بيانات الإنتاج يدوياً** لتصليح عطل. أي تصحيح بيتعمل بـ migration (forward-fix) أو بتسجيل واضح لمين عمل إيه.

### بيانات اتخربت أو اتمسحت

1. **وقّف الكتابة** (أوقف الـ API) قبل أي حاجة تانية، عشان ماتتفاقمش.
2. حدّد وقت الحادث من `audit_logs` و`subscription_events`.
3. استعد آخر نسخة سليمة في قاعدة **بديلة** وقارن ([backup-restore.md](./backup-restore.md)). فكّر في استخراج الصفوف المتضررة بس من النسخة بدل استبدال القاعدة كلها، لو الضرر محدود.
4. لو استبدلت القاعدة كلها: نفّذ «الإجراء الأمني بعد استعادة نسخة قديمة» في نفس الـ runbook، وبلّغ العملاء المتأثرين بأي تغيير ضاع بعد وقت النسخة.

### migration فشلت في النص

ADR-0009: وقّف النشر، شوف `__drizzle_migrations`، اكتب migration جديدة تكمّل أو تصلّح، أو استعد النسخة لو الحالة مش مفهومة. ماتعدّلش الملف اللي فشل.

### تسريب أو اشتباه اختراق

1. أبطل الـ access tokens فوراً: غيّر `JWT_ACCESS_SECRET` وأعد تشغيل الـ API (كل الـ access tokens الحالية بتبطل).
2. أبطل الـ refresh sessions: `UPDATE refresh_sessions SET revoked_at = UTC_TIMESTAMP(3) WHERE revoked_at IS NULL;` (نفس الـ SQL اللي اتجرّب في [backup-restore.md](./backup-restore.md)).
3. لو هاشات كلمات السر اتسرّبت: كلمات السر Argon2id، بس الأحوط إجبار تغييرها. **مفيش endpoint لإجبار إعادة تعيين كلمة السر لحد ما استعادة كلمة المرور تتبني (محتاجة مزوّد بريد).**
4. حافظ على اللوج و`audit_logs` للتحقيق قبل ما تمسح أي حاجة.

## البريد

**مفيش بريد في النظام حالياً.** استعادة كلمة المرور والتحقق من البريد ما اتبنوش، وكمان قرار مزوّد البريد لسه ما اتاخدش (انظر `TASKS.md`)، فمفيش حاجة تتعطل دلوقتي بسبب البريد، ولا فيه إجراء تشغيل يتوثّق.

هيتكمّل القسم ده لما المزوّد يتحدد، والمفروض يغطي:

- هل فشل إرسال البريد بيمنع التسجيل؟ (قرار تصميم: يفضل التسجيل ينجح والإرسال يتأجّل.)
- إعادة محاولة الإرسال وحدودها.
- SPF/DKIM/DMARC للدومين.
- التعامل مع bounce وشكاوى السبام.

## بعد الحادث

- اكتب ملخص قصير: إيه اللي حصل، ومن إمتى لإمتى، وإيه الأثر، وإيه اللي اتعمل، وإيه اللي هنغيّره عشان مايتكررش.
- حدّث الـ runbook المعني بأي خطوة طلعت ناقصة أو غلط.
- لو الحادث كشف ثغرة، سجّلها كبند في `TASKS.md` وأضف لها اختبار.
