# Runbook: النشر والتراجع

> **الحالة:** هيكل محايد للمنصة. منصة الاستضافة، والـ reverse proxy، وHTTPS، ومخزن الأسرار ما اتحدّدوش لسه، وكل بند متعلق بيهم معلَّم **ينتظر قرار**. الأوامر المعلَّمة «اتجرّب» اتشغّلت على جهاز التطوير بتاريخ 2026-10-27.

## قيود لازم تتعرف قبل أي نشر

1. **instance واحد بس للـ API.** مهمة انتهاء الاشتراكات (`startExpiryJob`) شغّالة جوه العملية كل دقيقة، وعدّادات الـ rate limit وحظر الدخول في ذاكرة العملية (ADR-0004). تشغيل أكتر من instance يعني عدّادات مش متزامنة. مخزن مشترك مطلوب قبل التوسّع.
2. **الواجهة والـ API لازم يكونوا same-site.** كوكي الـ refresh `HttpOnly` و`SameSite=Strict` وبيتفحص `Origin` على مساراته (ADR-0004). في الإنتاج الكوكي بياخد `Secure` وبادئة `__Secure-`، فمحتاج HTTPS. **ينتظر قرار:** الدومين والـ proxy.
3. **الـ migrations للأمام بس** (ADR-0009). مفيش `down`. التراجع عن التطبيق مش بيرجّع قاعدة البيانات.
4. **`JWT_ACCESS_SECRET`** تغييره بيبطّل كل الـ access tokens الحالية (مدتها 15 دقيقة افتراضياً). الـ refresh tokens مخزّنة في القاعدة فبتفضل تشتغل وبتجدّد الجلسة، فالمستخدم ما بيخرجش.

## متغيرات البيئة المطلوبة (من `backend/src/config/env.ts`)

الخادم بيرفض يشتغل لو أي قيمة غلط (fail fast).

| المتغير | ملاحظة |
|---|---|
| `NODE_ENV=production` | بيفعّل `Secure` على الكوكي وHSTS |
| `DATABASE_URL` | `mysql://...`، بمستخدم مخصوص بصلاحيات على قاعدة التطبيق بس، مش root |
| `JWT_ACCESS_SECRET` | 32 حرف على الأقل، ومش بيبدأ بـ `CHANGE_ME`. توليد: `node -e "console.log(require('crypto').randomBytes(48).toString('base64'))"` |
| `WEB_ORIGIN` | عنوان الواجهة بالظبط (مطابقة تامة لـ CORS وفحص `Origin`) |
| `API_HOST` / `API_PORT` | الافتراضي `127.0.0.1:4000`، يعني الخادم مش مكشوف إلا عن طريق الـ proxy |
| `TRUST_PROXY=true` | **فقط** لو فيه reverse proxy بتتحكم فيه. غير كده الـ rate limit هيشوف IP الـ proxy |
| `LOG_LEVEL`، `ACCESS_TOKEN_TTL_SECONDS`، `REFRESH_TOKEN_TTL_DAYS` | ليهم قيم افتراضية |

الأسرار بتتحط في مخزن الأسرار بتاع المنصة (**ينتظر قرار**)، مش في ملفات YAML ولا في المستودع.

## قبل النشر (Pre-flight)

- [ ] الـ CI أخضر على الـ commit المقصود (`check` و`audit`).
- [ ] لو فيه migration جديدة: اتعمل لها `pnpm db:lock`، ولو فيها أمر مدمّر فيها سطر `-- destructive-approved: <السبب>` (ADR-0009).
- [ ] لو الـ migration بتكسر النسخة القديمة من التطبيق: متقسّمة expand ثم contract (ADR-0009 بند 5)، يعني التراجع عن التطبيق هيفضل ممكن.
- [ ] **نسخة احتياطية** من القاعدة قبل أي migration على بيانات حقيقية ([backup-restore.md](./backup-restore.md)).
- [ ] رقم الـ commit الحالي المنشور متسجّل (لازم لو هنرجع له).

## خطوات النشر

من جذر المستودع على الـ commit المطلوب، ومتغيرات البيئة متظبطة:

1. **التثبيت:** `pnpm install --frozen-lockfile`
2. **البناء:** `pnpm build` (بيبني `backend/dist` و`frontend/dist`).
   - `VITE_API_BASE_URL` بيتثبّت في الواجهة وقت البناء، فلازم يتحدد قبل البناء.
3. **الـ migrations** (من مجلد `backend`):
   `node dist/database/migrate-cli.js`
   - **اتجرّب** ✅ 2026-10-27 على قاعدة التطوير: خرج `Migrations applied.` وexit code 0. آمن لو اتشغّل تاني (اللي اتطبق بيتخطاه).
   - بيقرا مجلد `backend/src/database/migrations`، فلازم يتواجد على السيرفر مع الـ build (يعني النشر من checkout للمستودع مش من `dist` لوحده).
   - لو فشلت في النص: وقّف، ماتشغّلش الإصدار الجديد، واتبع «لو migration فشلت في النص» في ADR-0009.
4. **تشغيل الـ API:** من مجلد `backend`: `node dist/server.js` (أو `pnpm --filter backend start`، وده بيقرا `../.env` لو موجود).
   - الإيقاف الآمن: `SIGTERM` أو `SIGINT` بيقفل مهمة الانتهاء والخادم وكتابات الـ audit المعلّقة وقاعدة البيانات قبل الخروج.
5. **تقديم ملفات الواجهة** من `frontend/dist` خلف نفس الدومين/site. **ينتظر قرار.**

## التحقق بعد النشر

| الفحص | المتوقع | حالة |
|---|---|---|
| `GET /api/v1/health` | `200 {"status":"ok"}` (الخادم شغّال) | اتجرّب ✅ |
| `GET /api/v1/health/ready` | `200 {"status":"ready"}`؛ لو القاعدة مش واصلة `503 {"status":"unavailable"}` من غير تفاصيل | اتجرّب ✅ (حالة 200) |
| `GET /api/v1/auth/me` من غير token | `401` | تحقق يدوي |
| `POST /api/v1/auth/login` من غير `Origin` | `403` | تحقق يدوي |
| تسجيل دخول فعلي بحساب فحص، وفتح صفحة الباقات العامة | يشتغل | تحقق يدوي |
| اللوج | مفيش أخطاء 5xx جديدة، ومفيش `subscription expiry pass failed` | تحقق يدوي |

لو أي فحص فشل، ابدأ التراجع.

## التراجع (Rollback)

**التطبيق:**

1. أعد نشر الـ commit السابق (المسجّل في الـ pre-flight) بنفس الخطوات (من غير migrate لو مفيش migration جديدة).
2. لو الإصدار الفاشل كان فيه migration: النسخة القديمة هتشتغل على القاعدة الجديدة **بس لو الـ migration كانت expand-only** (إضافة عمود أو جدول). لو كانت مدمّرة أو غيّرت معنى عمود، التراجع للنسخة القديمة مش آمن.

**قاعدة البيانات:** مفيش تراجع تلقائي (ADR-0009).

1. **الأفضل:** forward-fix، يعني migration جديدة تصلح المشكلة.
2. **لو الحالة مش مفهومة أو البيانات اتخربت:** استعادة النسخة الاحتياطية اللي اتاخدت في الـ pre-flight ([backup-restore.md](./backup-restore.md))، مع الانتباه إن أي بيانات اتكتبت بعد النسخة هتضيع.

## ما لم يُغطَّ بعد

- النشر التدريجي (blue/green أو canary) والـ health checks من الـ orchestrator: **ينتظر قرار المنصة** (بند §13 «نشر تدريجي أو آمن» لسه مفتوح).
- أتمتة النشر من الـ CI (الـ CI الحالي بيفحص بس ومبينشرش).
- HTTPS وتجديد الشهادات والدومين.
- بيئة staging.
