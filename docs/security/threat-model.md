# AXOR — Threat Model مبسّط

> الحالة: مسودة للمراجعة (2026-11-07). مبني على الكود الموجود فعلاً في `main` وعلى ADRs 0003–0024، مش على تصميم مستقبلي.
> القاعدة: أي تحصين مذكور هنا له اختبار أو حارس ساكن مذكور في `TASKS.md`. أي حاجة مش متنفذة مكتوبة تحت «فجوات معروفة».
> ده مش تقرير اختبار اختراق ولا مراجعة أمنية مستقلة (بند §9 «مراجعة أمنية قبل الإطلاق» لسه مفتوح).

## 1. النطاق

داخل النطاق (موجود في الكود):

- الحسابات والمصادقة: `/auth/*` (تسجيل، دخول، تجديد، خروج، تغيير كلمة المرور، الملف الشخصي).
- الشركات والأعضاء: `/members/*`، وإيقاف الشركة وإعادة تفعيلها من لوحة المنصة.
- الاشتراكات والتجارب: `/subscriptions/*` و`/admin/subscriptions/*`.
- الكتالوج العام والإدارة: `/catalog/*` و`/admin/catalog/*`.
- سجل التدقيق (قراءة): `/admin/audit-logs`.
- الواجهة (React، مسارات `#/...`) وقاعدة بيانات MariaDB.

خارج النطاق حالياً (مش متبني، فمفيش سطح هجوم فعلي لسه — التهديدات المتوقعة فيها مكتوبة في §6):

- ربط STARK وCAPRINA.
- الدومينات والنسخ المستقلة.
- الدفع الإلكتروني.
- البريد (التحقق من البريد واستعادة كلمة المرور).

## 2. الأصول

| الأصل | ليه مهم |
|---|---|
| بيانات كل شركة (مستخدمين، اشتراكات) | عزلها هو أهم ضمان في المنصة؛ تسريبها بين شركتين = حادث جسيم |
| حسابات المنصة (owner/admin) | بتتحكم في الكتالوج والاشتراكات وإيقاف الشركات |
| كلمات المرور (hash) وجلسات الـ refresh | اختراقها = انتحال هوية |
| أسرار الخادم (`JWT_ACCESS_SECRET`، بيانات اتصال قاعدة البيانات) | تزوير توكنات أو وصول مباشر للبيانات |
| تكامل الاشتراك (السعر والحدود وحالة الاشتراك) | الوصول للميزات المدفوعة مبني عليها |
| سجل التدقيق | الدليل على مين غيّر إيه |
| توافر الخدمة | تعطّل الدخول أو الكتالوج |

## 3. حدود الثقة

1. المتصفح ← الخادم: كل مدخل غير موثوق (body وparams وquery والكوكي والهيدرز).
2. الخادم ← MariaDB: الخادم هو الجهة الوحيدة المسموح لها بالوصول، والعزل بين الشركات بيتفرض في طبقة التطبيق (MariaDB مفيهاش Row-Level Security، ADR-0002).
3. نطاق المنصة ← نطاق الشركة: مستخدم المنصة مالوش شركة، ومستخدم الشركة مالوش صلاحية منصة (CHECK في جدول `users`، ADR-0003).
4. الواجهة نفسها غير موثوقة كوسيلة حماية: إخفاء زر ≠ صلاحية.

## 4. نقاط الدخول

المسارات العامة (من غير توكن): `GET /health`، `GET /health/ready`، `GET /catalog/products`، `GET /catalog/products/:productCode/plans`، `POST /auth/register`، `POST /auth/login`، `POST /auth/refresh`، `POST /auth/logout`.

مسارات محتاجة مصادقة: `/auth/me` و`/auth/change-password` و`/members/*` و`/subscriptions/*` (نطاق الشركة)، و`/admin/*` (نطاق المنصة، owner أو admin فقط).

## 5. التهديدات والتحصينات (STRIDE مختصر)

### 5.1 الحسابات والمصادقة

| التهديد | التحصين المتنفذ | ملاحظة |
|---|---|---|
| تخمين كلمات المرور | Argon2id بإعدادات OWASP، حد 5 محاولات فاشلة، وحد طلبات لكل IP على `/auth/*` | الحظر ثابت مش متدرج (فجوة 1) |
| تعداد الحسابات عبر الدخول | نفس رد 401 ونفس التوقيت لكل حالات الفشل، مع تنفيذ نفس الشغل لو الحساب مش موجود | |
| تعداد الحسابات عبر التسجيل | **غير محمي عن قصد**: التسجيل بيرد 409 صريح لو البريد محجوز (قرار موثق في ADR-0004) | مقايضة معلنة: تجربة استخدام مقابل التعداد |
| سرقة access token | عمره 15 دقيقة، موجود في الذاكرة بس (مش localStorage)، ومبيحملش دور ولا شركة (الـ Principal بيتبني من القاعدة كل طلب) | |
| تزوير JWT | رفض `alg=none` وHS512 والتوكن المعدّل، وفحص قوة السر في الإنتاج (ADR-0017) | |
| سرقة refresh token | opaque، HttpOnly وSameSite=Strict (و`Secure` و`__Secure-` في الإنتاج)، متخزن SHA-256 بس، وبيتغيّر مع كل استخدام | |
| إعادة استخدام refresh token قديم | كشف إعادة الاستخدام بيلغي عائلة الجلسات كلها | مختبر بطلبين متزامنين |
| CSRF على مسارات الكوكي | `SameSite=Strict` + فحص `Origin` (غايب أو مختلف = 403) | |
| بقاء جلسات بعد تغيير كلمة المرور | `POST /auth/change-password` بيلغي كل جلسات الـ refresh وبيسجّل `password_changed_at`، وأي access token اتصدر قبله بيترفض فوراً (الجهاز اللي غيّر بيفضل داخل) | مختبر في `change-password.integration.test.ts` |
| تعطيل مستخدم أو شركة | بيسري فوراً على الـ access token | مختبر |

### 5.2 عزل الشركات

| التهديد | التحصين المتنفذ |
|---|---|
| قراءة أو تعديل بيانات شركة تانية بمعرّف صحيح (IDOR/BOLA) | `TenantScope` مبيتبنيش إلا من المستخدم المصادَق عليه، ومينفعش يتبني من الـ body أو يتعدّل، وكل الـ Repositories بتقيّد بـ `tenant_id`. اختبارات عزل على MariaDB حقيقية، متماثلة بين الشركتين |
| العميل بيحط `tenantId` أو `role` أو `status` في الطلب (Mass Assignment) | كل schema هو `z.strictObject` (الحقل الزيادة = 400)، وحارس ساكن بيفشل لو route كتابة قرأ body من غير `parseInput` |
| رفع صلاحيات النفس | نطاقين أدوار منفصلين، `authorize()` رفض افتراضي (403)، وسياسة الأعضاء (`member-policy.ts`) |

### 5.3 الاشتراكات والتجارب

| التهديد | التحصين المتنفذ |
|---|---|
| تكرار التجربة | UNIQUE على (شركة + نظام) وعلى (بريد مطبّع + نظام) في `trial_claims`، والبريد بيتطبّع (trim وlowercase وشيل `+tag`) |
| تلاعب بالسعر أو الحدود من العميل | السعر والمدة والحدود مصدرها `plan_versions` في القاعدة، والعميل مبيبعتش إلا كود النظام |
| استمرار الوصول بعد الانتهاء | الوصول بيتقفل من الخادم حسب حالة الاشتراك |
| سباق (race) على إنشاء اشتراكين | UNIQUE(tenant_id, product_id) على `subscriptions` |

### 5.4 لوحة المنصة (الأعلى خطورة)

| التهديد | التحصين المتنفذ | ملاحظة |
|---|---|---|
| مستخدم شركة يوصل لـ `/admin/*` | بيرجع 403، وبدون توكن 401 | مختبر لكل دور |
| تغييرات غير مسجلة | كل تغيير إداري بيتسجل في `audit_logs` في نفس الـ transaction بالفاعل، من غير أسرار | |
| تغيير سعر بالغلط | كل تعديل بيعمل نسخة جديدة والقديمة ما بتتغيرش، وفيه رجوع لنسخة قديمة | |
| اختراق حساب منصة | لا شيء إضافي بعد كلمة المرور | **MFA غير متنفذ** (فجوة 2) |

### 5.5 الواجهة

| التهديد | التحصين المتنفذ |
|---|---|
| XSS | مفيش HTML خام في الواجهة، وCSP صارمة (`default-src 'none'` وكل حاجة `'self'`، من غير `unsafe-*`)، وحارس ساكن بيفشل لو ظهر `dangerouslySetInnerHTML` أو `innerHTML` أو `eval` |
| تسريب توكن في الـ URL | الـ access token في الـ header وفي الذاكرة بس، ومسار السجل بيتسجل من غير query string |

### 5.6 الخادم والبنية

| التهديد | التحصين المتنفذ |
|---|---|
| SQL injection | Drizzle (parameters) + حارس ساكن بيفشل لو ظهر `sql.raw` أو استعلام نصي غير ثابت + اختبارات هجوم |
| SSRF | مفيش وظيفة بتتصل بعنوان من المستخدم، وحارس ساكن بيفشل لو ظهر HTTP client أو `fetch(` |
| استنزاف الموارد | body حده 64KB وJSON بس، `maxParamLength` 100، وtimeouts للطلب والـ headers، وtimeout على استعلامات القاعدة، وحدود ترقيم على كل القوائم، وحارس N+1 (ADR-0015 وADR-0019 وADR-0020) |
| تسريب بيانات في الأخطاء والسجلات | أخطاء 5xx برسالة عامة، و`err` serializer بـ allowlist (Drizzle كان بيسرّب params قبل الإصلاح)، وإخفاء `authorization` و`cookie` و`password` و`token` |
| أسرار في المستودع | `scripts/secret-scan.mjs` في pre-commit وفي `pnpm check` وفي CI على كل التاريخ |
| إعدادات إنتاج ضعيفة | الخادم بيرفض يشتغل في الإنتاج لو `WEB_ORIGIN` مش https أو `LOG_LEVEL` debug أو المستخدم root أو السر ضعيف (ADR-0016 وADR-0017) |
| ثغرات dependencies | `pnpm audit --prod --audit-level=high` في CI، وDependabot متفعّل لـ npm (frontend وbackend) وGitHub Actions (ADR-0008) |

## 6. تهديدات متوقعة لما يتبني الباقي (مفيش تحصين لسه)

دي مش ثغرات حالية، بل بنود لازم تتصمم صح قبل ما تتنفذ:

- **STARK**: ربط الهوية من غير JWT في الـ URL، والتحقق من الاشتراك في كل طلب شحن، وعزل جداول الشحن بـ `tenant_id` (ADR-0003 سؤال #6 معلّق على مراجعة كود STARK).
- **الدومينات والنسخ المستقلة**: انتحال ملكية دومين (لازم تحقق بـ DNS قبل الربط)، وسيطرة على subdomain متروك (takeover)، وتسرب أسرار بين العملاء المستقلين.
- **البريد**: روابط الاستعادة (عمر قصير واستخدام واحد)، وحقن هيدرز في الرسائل، وتعداد الحسابات من «نسيت كلمة السر».
- **الدفع**: تكرار الخصم (idempotency)، وتزوير webhook (فحص توقيع)، وعدم تخزين بيانات البطاقة.

## 7. فجوات معروفة (مفتوحة)

1. حظر محاولات الدخول ثابت مش متدرج، والعدّاد في ذاكرة العملية؛ لو اتشغّل أكتر من instance لازم مخزن مشترك.
2. مفيش MFA لحسابات المنصة.
3. مفيش error monitoring ولا تنبيهات (بند §12).
4. HTTPS مش متحقق منه لأن مفيش بيئة نشر لسه؛ بروتوكول الكوكي الآمن مختبر في وضع الإنتاج بس.
5. مفيش مراجعة أمنية مستقلة ولا اختبار OWASP/API Top 10 منهجي قبل الإطلاق.
6. مفيش سياسة خصوصية أو احتفاظ بالبيانات معتمدة (قرار قانوني/تجاري).
7. صلاحيات الوصول للملفات والنسخ الاحتياطية لسه ما اتراجعتش على بيئة حقيقية.
8. التسجيل بيكشف إن البريد محجوز (قرار معلن، لكن ممكن تتغير حسب سياسة الخصوصية).

## 8. الصيانة

- يتراجع الملف عند إضافة أي endpoint جديد أو أي نظام (STARK وCAPRINA) أو أي مزوّد خارجي (بريد، دفع، استضافة).
- كل ثغرة جديدة تتحط في «فجوات معروفة» بتاريخها، وتتشال لما يتنفذ تحصينها وله اختبار.
